Use Case #37, Team-070-BrendanEich. An independent prototype by Michael Krampah. It uses an abstract simulated network and assumed parameters. It contains no real systems, no exploit code and no client data, and makes no claims about real defences.

In a cyber exercise the white cell is the neutral referee. Here it injects an attack into a simulated network, runs repeated exercises against three autonomous defence policies, enforces a guardrail and scores them.

1. Problem

Autonomous cyber defence is only useful if it can be trusted, and trust needs testing that is safe, repeatable and fair. In an exercise, the white cell is the neutral control team: it sets the scenario, injects events, enforces the rules, adjudicates what happens and scores the defenders. Can an automated white cell run repeatable exercises that score autonomous defence policies, including how much human oversight to keep, before they go near a real network?

2. Method

The world is an abstract network of 10 systems in four zones, where the Database and the Domain controller are critical. The white cell injects a starting foothold. A simple red agent then tries to spread one step per tick. Three blue policies defend, differing in how likely they are to detect an intrusion, how often they raise false alerts, and what they may do without a human (table below). An isolated system is offline for 5 ticks. The white cell logs every event, repeats the exercise many times per policy and scores each one with the stated weights. The rule it enforces is that an autonomous action must not wrongly take a healthy critical system offline.

4. Limits

  • Assumed, not measured. Detection rates, false alert rates, spread chances and system weights are invented. The output shows how the model behaves, not how real defences behave.
  • Built-in conclusion risk. The guardrail and the score weights are my choices, so the ranking partly reflects them. Change the approval delay to see how fragile it is.
  • Toy attacker. The red agent spreads at random. It is not a skilled adversary and does not model real attack techniques.
  • Rule-based defenders. The policies are fixed rules, not learned or LLM-driven agents. Human analysts are assumed to triage perfectly after the delay.
  • Not validated. Nothing has been compared with real incident timelines or with established open cyber-defence environments.
  • No confidence intervals. Small gaps between policies should not be trusted.

# Autonomous Cyber Defence White Cell: prototype

Use Case #37, Team-070-BrendanEich. Independent prototype by Michael Krampah.

An automated white cell (the neutral referee of a cyber exercise) that runs repeatable simulated attacks against three autonomous defence policies, enforces a guardrail and scores them.
Abstract simulation only. No real systems, no exploit code, no client data.

## Run it
Open the HTML file in any browser. No install, no server, no API keys.

## What it does
1. The white cell injects a scenario (a starting foothold) into an abstract 10-system network.
2. A simple red agent spreads from system to system.
3. Three blue policies defend: Conservative (a human approves every action), Balanced (automatic on ordinary systems, human approval on critical ones), Aggressive (automatic everywhere).
4. The white cell logs every event and runs N exercises per policy.
5. It scores each policy on attacker success, containment, mission uptime and guardrail breaches, and writes an after-action summary.
6. Change the human approval delay to see the trade-off between oversight and speed.

## Scoring
score = 100 x (0.40 x (1 - attacker reached database) + 0.25 x uptime + 0.20 x contained + 0.15 x (1 - guardrail breaches, capped at 1))
A guardrail breach is an autonomous action that takes a healthy critical system offline.
The weights are assumptions. Change them in the HTML file.

## Assumptions
Detection rates, false alert rates, spread probabilities, system weights and the 5-tick isolation time are illustrative, not measured.
